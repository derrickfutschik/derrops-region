# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An AWS CDK (TypeScript) app for **region-level** infrastructure — the setup that
makes a given AWS region usable for workloads. Deployed once **per region**, with
the region supplied explicitly at deploy time. The CDK app entry is
`bin/region-bootstrap.ts`; each stack lives in `lib/*.ts`; each stack has a doc
under `docs/` and a test under `test/`.

Its counterpart repo is **`derrops-account`** (`../derrops-account`), which holds
account-level infrastructure (billing, budgets, alerting, global SSM parameters),
is deployed once per account, and is pinned to `us-east-1`. If a resource is
account-global — deployed once no matter how many regions you use — it belongs
there, not here. If it must exist once in each region you light up, it belongs
here.

## Commands

- `npm run build` — compile TypeScript (`tsc`). Run before committing; a clean build is the first gate.
- `npm test` — run all Jest tests. (Tests set their own region; no context needed.)
- Run one test file: `npx jest test/vpc-stack.test.ts`
- Run tests matching a name: `npx jest -t 'derives AZ names'`
- `npx cdk list --long -c region=<aws-region>` — list stacks with construct id, deployed stack name, and target environment.
- `npx cdk synth <stack> -c region=<aws-region>` — synthesize the CloudFormation template (use to verify generated resource names).
- `npx cdk diff -c region=<aws-region>` — compare deployed stacks in that region against current state.
- `npx cdk deploy --all -c region=<aws-region>` — deploy a whole region.

**Every `cdk` command needs `-c region=<aws-region>`.** The app throws without
it. Never add a default *to the app*.

The `npm` wrappers (`npm run deploy` / `deploy:stack` / `diff` / `synth` /
`list`) supply `-c region=ap-southeast-2` in `package.json`, matching the
`scripts/` default. That is a convenience at the call site only — the region
still arrives at `bin/region-bootstrap.ts` as an explicit context value. Keep it
that way: the default belongs in `package.json`, never in the app. Override with
`-- -c region=<other>` (the later `-c` wins).

## The region is an explicit input

`bin/region-bootstrap.ts` reads `app.node.tryGetContext('region')` and throws if
it is missing. Do not add a fallback to `CDK_DEFAULT_REGION`, `AWS_REGION`, or a
literal — every stack name in this repo is *identical in every region*, so a
silently-defaulted region is invisible in `cdk diff` and lands infrastructure in
the wrong place.

Corollaries for anything added here:

- **Nothing may hardcode a region**, in a name, a string, or a lookup.
- **Nothing may assume an AZ group.** AZ suffixes carry the region's group number
  (`1a` in `us-east-1`, `2a` in `ap-southeast-2`). Derive it from `this.region`
  the way `lib/vpc-stack.ts` does; a constant `'1a'` builds `ap-southeast-1a` in
  `ap-southeast-2` — a real AZ in a *different* region.
- **Guard against token regions.** A stack that reads `this.region` must reject
  an unresolved token (`cdk.Token.isUnresolved`) rather than emit a garbage
  template. `VpcStack` does this and has a test for it.
- Prefer deploy-time-resolved, region-portable references over anything pinned:
  e.g. `ec2.MachineImage.latestAmazonLinux2023()` resolves an AWS-owned public
  SSM parameter per region, so it is correct everywhere. Never hardcode an AMI id.

## Naming: the core rule

**Never hand-assemble a name** (no `` `${org}--${domain}--...` `` template strings). Every AWS resource name, stack name, CDK construct id, tag, and per-stack doc filename is generated by [`derrops-conventions`](https://www.npmjs.com/package/derrops-conventions). When naming anything, use the **`naming-aws-resources` skill** — it maps an AWS resource to the correct `type` key, delimiter, and segments.

- The org segment is always `derrops` and the domain segment is always `region`. Each stack picks its own `service`.
- Segments join with `--`; words inside a segment join with `-`. Path/DNS-native services (`/`, `.`) get their delimiter chosen by the library per `type` — never pick one yourself.
- Look up the resource `type` key against the library (README table / the built package) before using it. Some types in the code are absent from the README table (e.g. `cloudwatchAlarm`), and some README suffixes are aspirational — **verify actual output** via a test that asserts on the synthesized name, not by trusting the table.
- **Never put a `/` inside a `key`** to fake a hierarchy. Use additional segments so the library builds the path (for `ssmParam`, `purpose` renders *after* `key` — see the `subnet-ids` params in `lib/vpc-stack.ts`).

### Names are not region-qualified — and that is deliberate

Do **not** try to work a region into a name to disambiguate deployments. Almost
everything AWS names is region-scoped: CloudFormation stacks, VPCs, subnets,
security groups, SSM parameters, CFN exports. The same convention name in two
regions is two independent resources, which is exactly what we want. (The
library only emits its `region` segment for globally-unique types like S3
buckets, so it would not help you here anyway.)

### The exception: account-global resource names

**IAM roles/users/policies and S3 bucket names are not region-scoped.** A fixed
convention name on one of those succeeds in the first region and fails with
`EntityAlreadyExists` in the second. So in this repo:

- Leave account-global resources **unnamed** and let CDK generate a unique
  physical name. Find them by their `derrops:*` tags instead.
- Add a comment at the construction site explaining why the name is absent, and
  a test asserting the name property stays absent from the template
  (`RoleName: Match.absent()` — see `test/bastion-stack.test.ts`).

`lib/bastion-stack.ts`'s `BastionRole` is the worked example.

## Parameters / config

Shared config lives in SSM Parameter Store, meant to be read at **runtime** (SSM SDK/CLI) — do **not** wire values into templates via CloudFormation dynamic references (`valueForStringParameter` / `{{resolve:ssm}}`) or synth-time `valueFromLookup`.

- **Account-level** params (alert recipients, etc.) are owned by the
  `derrops-account` repo and live in SSM **in `us-east-1`**. Read them at runtime
  with an explicit `--region us-east-1`. CloudFormation dynamic references cannot
  cross regions at all, so there is no synth-time shortcut even if you wanted one.
- **Region-level** params are published by the stack that owns the underlying
  resource, into the region being deployed (`VpcStack` publishes its VPC and
  subnet ids; `BastionStack` publishes its instance id). The same parameter name
  exists independently in each region — every read needs an explicit `--region`.
- Derived values that should track the stack use plain `ssm.StringParameter`.
  Editable config would need the create-if-absent seeding pattern instead
  (`SeedParameter` in the `derrops-account` repo); nothing here needs it yet.

## Per-stack source of truth

Each stack file exports a **single `DerropsConventions` instance** (`naming`) carrying that stack's `org`/`domain`/`service`. Everything derives from it, so the segments are defined once:

- resource names → `naming.name({ type, key })`
- stack name **and** CDK construct id → `naming.name({ type: 'cloudFormationStack' })` (the construct id in `bin/` imports the exported `naming` so it matches the stack name)
- tags on every resource → `naming.applyTags((k, v) => cdk.Tags.of(this).add(k, v))`

The stack sets its own name via `stackName: props.stackName ?? naming.name({ type: 'cloudFormationStack' })` in the `super()` call (spread `...props` **first**, then `stackName`, so an undefined `props.stackName` doesn't clobber the default).

The only identifier that is *not* the convention name is the TypeScript **class** (e.g. `VpcStack`) — `--` isn't a legal identifier. Its construct id, stack name, tags, and doc file are all the convention name.

## Shared resources across stacks

Don't duplicate region-wide singletons (e.g. the VPC) per stack. One stack **owns** the resource and exposes it (a `public readonly`); consumers receive it via props. `VpcStack` (`derrops--region--network`) owns the VPC and subnet arrays; `BastionStack` consumes them.

- The owner exposes the resource for in-app consumers **and** publishes a discovery handle for out-of-app areas: an `ssmParam` named by the convention.
- When a stack consumes another's resource, add an explicit `consumer.addDependency(owner)` in `bin/` so the owner deploys first — don't rely on the implicit reference alone.
- Cross-**region** sharing is not a thing here: stacks in this app only ever reference resources in their own region. If you need something from another region, read it at runtime via the SDK with an explicit region.

## Adding a new stack

1. Create `lib/<name>.ts`. Export one `naming` instance (`org: 'derrops'`, `domain: 'region'`, plus this stack's `service`). Derive every name/tag from it.
2. Instantiate it in `bin/region-bootstrap.ts`, importing the exported `naming` and passing `naming.name({ type: 'cloudFormationStack' })` as the construct id. It receives the shared `env` (whose region came from context).
3. Add `docs/<generated-stack-name>.md` (filename = the generated stack name, e.g. `docs/derrops--region--network.md`) and a row in the README "Stacks" table.
4. Add `test/<name>.test.ts` asserting on the synthesized template (see below).
5. Verify: `npm run build && npm test && npx cdk list --long -c region=ap-southeast-2`.

Before adding it, check it is genuinely region-scoped. Account-global setup goes in `derrops-account`.

## Testing approach

Tests synth a stack with `Template.fromStack(...)` and assert on **synthesized CloudFormation properties**, including convention-generated names (e.g. `Name: '/derrops/region/network/vpc-id'`). When you change a name or a default, update the matching assertions.

Region-specific expectations on top of that:

- Every test passes an explicit `env` with a concrete region — the stacks reject a token region by design.
- Any stack that touches AZs, region-derived values, or account-global names needs a **second-region test** (`ap-southeast-2` is the convention here) asserting the region-derived output is right. `test/vpc-stack.test.ts` asserts `ap-southeast-2a/b/c`; without it the hardcoded-AZ bug is invisible.
- Assert account-global name properties stay `Match.absent()`.
